# Fixed Evaluation Scenario: To-Do List Web App

> **Do not edit this file to "make the eval easier" or to match whatever the team
> produced.** Its entire value is being byte-identical across runs, so results are
> comparable across Horseless Carriage versions over time. If the scenario itself
> needs to change, that's a deliberate decision with its own commit message
> explaining why — never a silent drift.

This is the fixed input fed verbatim to the agent team as the product vision for
every automated team-performance evaluation run (see `RELEASE.md` "Team performance
evaluation" and `agents/scrum_team/scripts/run_eval.py`). It is intentionally small
enough to be fully deliverable within a 5-sprint, small-budget run, while still
requiring real design decisions (state persistence, list vs. item modeling,
basic UI) that differentiate a good team performance from a mediocre one.

## Product Vision

Build a simple to-do list web application. A single user should be able to:

1. Create a new to-do list with a name.
2. Add a task to a list, with a short text description.
3. Mark a task as complete or incomplete.
4. Delete a task.
5. Delete an entire list (and its tasks).
6. See all their lists and, within a list, all its tasks, with completed tasks
   visually distinguished from incomplete ones.

## Constraints (deliberately narrow, to keep this deliverable in 5 sprints)

- **Single user, no authentication.** Do not build login/accounts — out of scope.
- **No persistence requirement beyond the current session/process is assumed** unless
  the team's own design calls for it — persistence approach (in-memory, file, or a
  simple embedded DB) is a legitimate design decision for the team to make and
  justify, not a hidden requirement.
- **A working web UI is required** — the deliverable is something a person could
  open in a browser and actually use, not just a backend API with no way to
  interact with it.
- **No specific language/framework is mandated.** The team should choose something
  it can deliver completely and correctly within budget, and should say why.

## Explicitly out of scope (do not let these creep in)

- Multiple users, sharing, or permissions.
- Due dates, reminders, priorities, tags, or sub-tasks.
- Mobile app, offline support, or real-time sync.
- Any deployment/hosting beyond running locally.

## What "done" looks like after 5 sprints

A person can clone the repo, follow the README, run the app, and actually create a
list, add a few tasks, mark one complete, delete one, and delete a list — end to
end, without reading any code first.
