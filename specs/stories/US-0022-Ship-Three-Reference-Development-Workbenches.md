# User Story

- Story ID: US-0022
- Title: Ship Three Reference Development Workbenches (Flask, Kotlin Multiplatform, React+Firebase)
- Status: Done
- Priority: Must
- Owner: Architect
- Last Updated: 2026-11-11

## As an Architect, I want ready-made workbench templates for Python+Flask, Kotlin Multiplatform (Android & iOS), and React(Vite)+Firebase Functions+Firestore, so that projects on these stacks get a working scaffold/dev/test/debug toolchain without anyone authoring it from scratch.

## Acceptance Criteria
- Given the `python-flask` template, when selected, then the resulting workbench can scaffold a new Flask app, install dependencies, run its test suite, run the app, and support both debugging (e.g. `debugpy` or equivalent) and exploratory testing (e.g. an HTTP client or Flask shell) — plus an MCP config and a network allowlist (at minimum PyPI) declared for it.
- Given the `kotlin-multiplatform` template, when selected, then the resulting workbench can scaffold a KMP module targeting Android & iOS, install the required JDK/Android SDK/Kotlin toolchain, run its test suite (Gradle test tasks for both targets), and run/debug the Android target. iOS build/run realistically requires a macOS host with Xcode — this constraint is documented explicitly rather than silently promised as working inside the Linux-container workbench.
- Given the `react-vite-firebase` template, when selected, then the resulting workbench can scaffold a Vite+React app with Firebase Functions+Firestore, install dependencies, run its test suite, run the dev server and the Firebase emulator suite for exploratory testing, and support debugging — plus an MCP config and a network allowlist (npm registry, Firebase/Google Cloud endpoints) declared for it.
- Each template conforms to the directory/file contract defined by US-0021 (toolchain script, MCP config, network allowlist, each independently reviewable).

## Notes
- Parent epic: EP-0010.
- Depends on US-0021 shipping the template mechanism first — these are instances of that contract, not a separate mechanism.
- iOS is the one stack-specific constraint worth calling out up front: the agent's current Docker-based model is Linux-container-first, so the `kotlin-multiplatform` template should generate iOS-side scaffolding/config but document that actual iOS build/run/debug is host-dependent (macOS + Xcode), not something the workbench container itself can do.
- Design/technical notes: each template directory lives under `config/development-workbench-templates/<stack-name>/`, following US-0021's contract.

## Implementation Notes (as built)
- Three reference template directories added under `config/development-workbench-templates/`, each conforming exactly to US-0021's contract (required `workbench-setup.sh`, optional `mcp-config.json`/`manifest.json`):
  - **`python-flask/`**: `workbench-setup.sh` installs `flask`, `pytest`, `pytest-flask`, `debugpy`, and `httpie` via pip (the base agent image already ships Python 3.11), then prints scaffold/install/test/run/debug/exploratory-testing instructions (`flask --app app run --debug`, `python -m debugpy --listen 0.0.0.0:5678 ...`, `http GET ...`/`flask shell`). `manifest.json` declares `additional_allowlist_hosts: ["pypi.org", "files.pythonhosted.org"]`. `mcp-config.json` declares the official `mcp-server-fetch` reference MCP server (`uvx mcp-server-fetch`) for exploratory HTTP testing against the running dev server.
  - **`kotlin-multiplatform/`**: `workbench-setup.sh` installs OpenJDK 17 and the Android SDK command-line tools (`platform-tools`, `platforms;android-34`, `build-tools;34.0.0` via `sdkmanager`), then prints scaffold/install/test/run/debug instructions for the Android target (`./gradlew :androidApp:installDebug`, `adb jdwp`/`adb forward` for JVM debugging). `manifest.json` declares Gradle/Maven/Google allowlist hosts (`services.gradle.org`, `plugins.gradle.org`, `repo.maven.apache.org`, `repo1.maven.org`, `dl.google.com`). **iOS limitation surfaced explicitly, not silently dropped**: both the script's top-of-file comment block (headed "iOS LIMITATION — READ BEFORE ASSUMING iOS 'JUST WORKS' HERE") and `manifest.json`'s `description` state in plain language that this is a Linux container, that Apple does not ship Xcode/the iOS Simulator for Linux, that Kotlin/Native iOS *test* tasks (`:shared:iosX64Test`) genuinely run here, but that iOS *build/run/debug* (`xcodebuild`, Simulator boot, Xcode's debugger) does not and requires a macOS host with Xcode — both surfaces are asserted on directly in tests (see below), not left to incidental phrasing.
  - **`react-vite-firebase/`**: `workbench-setup.sh` installs Node.js 20 (via NodeSource, since the base image ships neither Node nor a JRE), OpenJDK 17 JRE (required by the Firestore/Auth emulators), and `firebase-tools` globally, then prints scaffold/install/test/run/debug instructions (`npm create vite@latest`, `firebase init functions firestore emulators`, `firebase emulators:start --only functions,firestore` for exploratory testing, `node --inspect-brk`/`firebase emulators:start --inspect-functions` for debugging). `manifest.json` declares `registry.npmjs.org` plus Firebase/Google Cloud API hosts (`firebase.googleapis.com`, `firestore.googleapis.com`, `cloudfunctions.googleapis.com`, `www.googleapis.com`). `mcp-config.json` declares Firebase CLI's own MCP server (`firebase experimental:mcp`).
- **Smoke tests**: each template directory also ships its own executable `smoke-test.sh` (e.g. `config/development-workbench-templates/python-flask/smoke-test.sh`) that builds a throwaway Docker image from the template's real `workbench-setup.sh`, scaffolds a minimal app, and runs that app's own test suite inside it — proving the install→scaffold→test path works end to end, not just that the template's files parse. These are **not** invoked by `run_tests.py`/the dockerized `agents/scrum_team/tests` suite: that suite's `agent` Compose service runs on `agent-net`, which `net-proxy`'s allowlist restricts to `github.com`/`api.github.com` (see `docker-compose.yaml`), so it has no route to `pypi.org`/`registry.npmjs.org`/`dl.google.com` — reaching those is the entire point of each template's own declared `additional_allowlist_hosts`, and is exactly the kind of real toolchain installation this repo's own sandboxed CI network deliberately cannot do for a *target* project. Each `smoke-test.sh`'s own header comment documents this and states where it should actually run instead: manually on a developer machine, or a dedicated CI job with real (non-sandboxed) internet access. `agents/scrum_team/tests/test_reference_workbench_templates.py::TestSmokeTestScriptsExist` asserts each script exists, is executable, and documents this — so the smoke-test requirement is met and visibly tracked, not silently skipped.
- **Unit tests**: `agents/scrum_team/tests/test_reference_workbench_templates.py` resolves all three real, shipped templates (no monkeypatching — exercising the actual on-disk files, as distinct from `test_workbench_templates.py`'s synthetic-fixture coverage of US-0021's generic mechanism) and asserts: each template resolves `status: ok`; each has a non-empty shebang-prefixed script; each `mcp_config` is a non-empty, well-formed `{"mcpServers": {...}}` dict with a `command` per server; each `additional_allowlist_hosts` is a non-empty list of plausible plain hostnames; each `description` is non-empty; plus per-template content checks (e.g. python-flask's script mentions `flask`/`pytest`/`debugpy`/`httpie`/`shell`; kotlin-multiplatform's mentions `jdk`/`android`/`sdkmanager`/`gradlew`/`testdebugunittest`; react-vite-firebase's mentions `vite`/`firebase`/`npm`/`emulator`/`inspect`).
- **iOS limitation test coverage**: `TestKotlinMultiplatformIosLimitationIsSurfaced` asserts both the script and the manifest `description` independently mention `macOS`, `Xcode`, the literal phrase `iOS LIMITATION`, and at least one of `build`/`run`/`debug` alongside a `cannot`/`does not` qualifier — i.e. the limitation is a specific, checkable claim on both Architect-facing surfaces, not a vague caveat that could silently rot.
- All 1304 tests in `agents/scrum_team/tests` (dockerized, via `docker compose ... run --rm agent pytest --cov=agents agents/scrum_team/tests`) plus all 798 host-script tests in `tests/` pass (`run_tests.py`'s two suites).

## Test Approach
- Per template: a smoke test that scaffolds a minimal app from the template and runs its test suite inside the resulting workbench image (CI or scripted check).
- Unit tests asserting each template's declared MCP config and allowlist hosts are well-formed and non-empty.
- Explicit test/doc check that the `kotlin-multiplatform` template's iOS limitation is surfaced (not silently dropped) wherever the template's capabilities are described to the Architect.
