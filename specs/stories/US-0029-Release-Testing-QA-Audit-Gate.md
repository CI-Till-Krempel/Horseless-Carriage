# User Story

- Story ID: US-0029
- Title: Release Testing - QA Audit/Regression Gate Before Shipping (GH-273)
- Status: Done
- Priority: Should
- Owner: QA
- Last Updated: 2026-11-12

## As a QA role, I want to run a whole-increment audit/regression pass immediately before a release PR opens, so that defects or gaps that slipped past each story's own Definition-of-Done testing are caught, tracked, and visible before the increment ships - not discovered after.

## Acceptance Criteria
- Given a sprint has reached SPRINT CLOSE SEQUENCE step 8 (after Scrum Master's KPIs/sprint-report step, before Product Owner's `create_release_pr`), when QA calls the new `run_release_audit()` tool, then it re-runs, across the WHOLE repo (not one story): the full test suite (`_execute_test_suite_coverage`), the dependency install (`check_build`), a security scan (`_scan_security_vulnerabilities`), and a sweep for trivial/stubbed test functions (`detect_stubbed_tests`).
- Given `run_release_audit` finds a deterministic defect (the full test suite genuinely has failing tests, or the build is genuinely broken), when `create_release_pr` is called, then it refuses outright, at EVERY interaction level (including CEO/EVAL) - naming the concrete defect(s) and requiring a fix + a fresh audit before retrying. A real defect is never silently shipped as "clean."
- Given `run_release_audit` finds only judgment-based gaps (a security-scan hit, a stubbed test - deciding "is this bad enough to block" is inherently a judgment call, not a fixed threshold), when `create_release_pr` is called, then it does NOT block - instead it (a) auto-appends a "Known Issues (Release Audit)" section naming every finding to the release PR body, so the release never goes out silently clean when it wasn't, and (b) each finding has already been filed as a tracked Issue (`upsert_issue`, landing in `specs/requirements/` and the backlog/roadmap the same way a retro-logged "technical" finding already is) and, best-effort, as a real GitHub issue (`gh_issue_create`).
- Given no audit has been run yet this release cycle, when `create_release_pr` is called at an interaction level with a human release-review step (today: "Product"), then it refuses, naming `run_release_audit()` as the exact call to make first - mirroring `required_pre_release_approval`'s existing "must be NEW since last release" baseline pattern (`release_audit_run_count`/`release_audit_baseline`). This freshness requirement is deliberately NOT enforced at CEO/EVAL levels (see Notes) - only the deterministic blocking-defect check above applies unconditionally everywhere.
- Given `run_release_audit`'s own checks individually fail to execute (e.g. `bandit`/`radon` not installed, the repo has no recognized test runner), when it's called, then it still returns a well-formed `status: "ok"`/`"blocked"` result (never raises) - a tool that can't run degrades to "nothing to report from that check," it never silently lets a broken release through by crashing past the gate.
- Given Product Owner reaches `create_release_pr`'s audit-freshness gate without QA ever having had a turn (e.g. inside the sprint's own budget-exhaustion grace allowance), when Product Owner calls `run_release_audit()` directly, then it succeeds the same way QA's call would - Product Owner has this tool too, specifically so the gate can never become an unrecoverable deadlock the way SPEC-ISSUE-0068 found for a similarly-shaped gap.

## Notes
- Distinct from EP-0002's existing per-story Definition-of-Done testing (`advance_story_stage`'s Tested gate: `check_build` + a real per-story test run) - that's a one-story snapshot; this is the final, whole-increment regression/gap pass right before the release ships.
- **Hard-block vs. advisory design rationale**: this codebase's established convention (`check_build`, the per-story Tested gate's test-failure check, `required_pre_release_approval`) is to hard-block only on fully-deterministic, mechanically-checkable facts, and advisory-flag (non-blocking, surfaced for a human/agent's judgment) anything that needs severity triage - `detect_stubbed_tests` is already exactly this pattern at the per-story level. An "audit for gaps/defects" is inherently judgment-based by nature (deciding whether a given security-scan hit or a stubbed test is release-blocking requires context this tool doesn't have), so `run_release_audit`'s own findings split the same way: a genuinely failing test suite or broken build is a deterministic fact (hard-blocked, every level); everything else is advisory (never silently dropped - tracked as a real Issue and surfaced directly in the release PR body, so "shipped clean" is never a false claim).
- The audit-freshness *process* requirement (was a fresh audit even run this cycle) is scoped like `required_pre_release_approval` - required only at interaction levels with a human release-review step ("Product" today), not at CEO/EVAL, where nothing drives a deliberate extra sequencing step and a hard requirement risks exactly the kind of abrupt, noisy-check stall this story's own GitHub-issue discussion (comment thread on #273) flagged as the real cost of a careless hard gate on something inherently judgment-based.
- New tool: `run_release_audit()` (`agents/scrum_team/tools/quality.py`), owned by QA (also given to Product Owner as a reachable escape valve, mirroring the `recheck_test_suite`/Architect fix for SPEC-ISSUE-0068).
- New tool: `gh_issue_create()` (`agents/scrum_team/tools/github.py`) - a thin `gh issue create` wrapper, the first real-GitHub-Issues tool in this codebase (everything else under `gh_*` wraps a PR/release operation). Best-effort only; a GitHub-side failure never affects the audit's own result.
- New `ScrumState` fields: `release_audit_run_count`, `release_audit_baseline`, `last_release_audit_result`.
- New `helpers.py` function: `required_pre_release_audit(level)`.
- `create_release_pr` (`agents/scrum_team/tools/github.py`) gates on both the blocking-defects check and the freshness check described above, and injects the "Known Issues (Release Audit)" section into the PR body.
- SPRINT CLOSE SEQUENCE (`ScrumOrchestrator-workflow.md`) gained a new step 8 (QA's release audit, between the sprint report and `create_release_pr`, now step 9); `QA-workflow.md`/`ProductOwner-workflow.md` updated accordingly.

## Test Approach
- `agents/scrum_team/tests/test_quality.py`: `run_release_audit` returns `status: "blocked"` with `blocking_defects` populated when the test suite/build check fails; returns `status: "ok"` with `advisory_findings` populated for a security-scan/stubbed-test hit; returns a clean `status: "ok"` with no findings when everything passes; persists `release_audit_run_count`/`last_release_audit_result` on every call; files advisory findings via `upsert_issue` and (only for genuinely new ones) attempts `gh_issue_create`, without raising if that fails; degrades safely (no exception, well-formed result) when an underlying check itself can't run.
- `agents/scrum_team/tests/test_github.py`: `gh_issue_create` wraps `gh issue create` correctly; `create_release_pr` refuses with `blocking_defects` present (every interaction level); refuses for a stale/missing audit at the "Product" level; proceeds at CEO/EVAL levels without requiring a fresh audit (only the blocking-defects check still applies there); appends the "Known Issues (Release Audit)" section to the PR body when `advisory_findings` are present, and does not duplicate the section on a second call; bumps `release_audit_baseline` on a successful release PR.
- Full `agents/scrum_team/tests` suite re-run (`python3 run_tests.py`) to confirm no regressions in the many existing `create_release_pr` tests, which now also need a fresh audit baseline in their fixture state (same pattern they already follow for `human_approvals`).
