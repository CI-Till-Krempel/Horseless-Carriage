# Manual Test Plan — v0.2.0

**Purpose:** a human walkthrough of everything the automated suites (`python3
run_tests.py`, the eval harness) can't fully verify on their own — real
interactive prompts, real Docker Desktop behavior, real GitHub pushes/PRs,
and cross-platform quirks. Run this before cutting `release/v0.2.0` → `main`
(see [RELEASE.md](../RELEASE.md)).

**How to use this document:** work through each test case in order within a
suite; suites can be split across testers/machines. Mark each row Pass/Fail,
and for any Fail, open an issue and link it in the Notes column. A release is
blocked if any **Critical** case fails; **High** failures need an explicit
call from whoever owns the release; **Medium** failures can ship with a
tracked follow-up issue.

**What counts as a release-blocking bug:** data loss or corruption in the
state repository, the agent bypassing a documented safety gate (budget caps,
DoD/DoR enforcement, protected-branch pushes), a setup/doctor script crashing
with a raw traceback instead of a clear message, `python3 run_tests.py`
failing on a clean checkout, or a release artifact (changelog, announcement)
being fabricated rather than honestly reflecting what shipped. Cosmetic/
wording issues are not release-blocking on their own.

**Relationship to [0.1.0-testplan.md](0.1.0-testplan.md):** TS-1 through TS-9
below are the same baseline regression suites from the v0.1.0 pass (setup,
diagnostics, a full sprint smoke test, GitHub integration, the local stack,
Windows, automated-suite sanity) — re-run every release since none of this
is version-specific. Only the priorities/framing that were v0.1.0-specific
("new in this release", "headline change") have been adjusted. **TS-10 is
new**: it covers this release's actual scope — automated `CHANGELOG.md`
generation, customer-facing announcement drafting, and end-user product
documentation tooling (EP-0004/EP-0005/EP-0006, see
[specs/ROADMAP.md](../specs/ROADMAP.md)).

## Test environment checklist

Before starting, have available:
- [ ] One **macOS or Linux** machine with Docker Desktop (or Docker Engine) installed
- [ ] One **Windows** machine with Docker Desktop installed (real Windows, not WSL2-as-the-shell — see [docs/SETUP.md § Setting up on Windows](../docs/SETUP.md))
- [ ] Real API keys for at least 2 of the 3 cloud providers (Gemini, Anthropic, OpenAI) — low-spend/sandboxed keys are fine, these tests make real (tiny) billed calls
- [ ] `gh` CLI installed and authenticated on each machine, with push/PR access to a disposable scratch GitHub repo created just for this test pass
- [ ] Enough free disk (~5-10 GB) for an Ollama model pull, if testing the local stack

## TS-10 — Release communication & documentation (new in this release)

This release's actual scope (EP-0004 Changelog Generation, EP-0005 Customer-Facing Announcement
Generation, EP-0006 Product Documentation Tooling — see
[specs/ROADMAP.md](../specs/ROADMAP.md)): automated `CHANGELOG.md` entries derived from real sprint
state, a customer-facing announcement drafted from that changelog, and an end-user product-doc tool
wired into the Definition of Done. Run these against the same scratch target repo as TS-5's sprint
smoke test — ideally across *two* consecutive sprints/releases, since several of the interesting
behaviors (dedup, reverse-chronological ordering) only show up on the second release.

| ID | Priority | Steps | Expected Result | Pass/Fail | Notes |
|---|---|---|---|---|---|
| TS10-01 | Critical | After TS5-01's sprint reaches Sprint Review & Release and Product Owner calls `create_release_pr`, inspect the target repo's `CHANGELOG.md`. | File exists (created on first use if it didn't already), with a `## Sprint N - YYYY-MM-DD` heading and a line item per story/fix actually `Accepted` this sprint — not freehand prose, and not empty/fabricated if nothing completed (an honest "No user-facing changes in this release" line instead). | | |
| TS10-02 | Critical | Confirm `CHANGELOG.md`'s diff landed in the **same** `develop → main` release PR as the rest of the sprint's work (not a separate follow-up commit/PR). | Visible in the PR's file list alongside the sprint report/transcript; `git log` shows no separate changelog-only commit after the PR merges. | | |
| TS10-03 | High | Run a **second** sprint/release against the same scratch repo, completing at least one more story. | The new entry is **prepended above** the first (reverse-chronological), and the first sprint's already-listed items are **not repeated** in the new entry — `sprint_backlog` accumulates across sprints, so this specifically guards against the same item showing up in every future changelog entry. | | |
| TS10-04 | High | After TS10-01, confirm Product Owner also drafted a release announcement (per `PO_PROMPT`'s Sprint Review & Release step). | `specs/announcements/ANNOUNCEMENT-sprint-N.md` exists in the target repo, follows `TEMPLATE-ANNOUNCEMENT.md`'s structure (Headline/What's New/Fixes & Improvements/Known Issues/Links), and reads as customer-facing (no raw story IDs/internal jargon as the primary wording). | | |
| TS10-05 | Medium | Compare the announcement's "What's New" section against the sprint's actual changelog entry/completed stories. | Internal-only work (refactors, test-only changes, tooling/chore stories) from the changelog does **not** appear in the announcement; genuinely user-facing items do. | | |
| TS10-06 | High | Temporarily break changelog generation (e.g. make the target repo's root read-only, or rename `CHANGELOG.md` to a directory) and re-run `create_release_pr`. | The release PR still opens successfully with the rest of the sprint's work; the tool result / sprint narrative surfaces a `changelog_warning` rather than the whole release failing. Restore normal permissions afterward. | | |
| TS10-07 | High | During a sprint where Dev Team completes a story with real user-facing behavior (e.g. a new CLI flag or endpoint), watch for a `specs/product-docs/GUIDE-*.md` file. | Dev Team calls `upsert_user_doc` for that story before marking it Implemented (per `DEV_PROMPT`/DoD); the file follows `TEMPLATE-USER-GUIDE.md`'s structure (Overview/Prerequisites/Steps/Examples/Troubleshooting/Related). | | |
| TS10-08 | Medium | During a sprint where Dev Team completes a *purely internal* story (refactor, test-only, no user-facing change). | Dev Team explicitly notes end-user docs are "not applicable" for that story rather than silently skipping the step or fabricating an irrelevant guide. | | |
| TS10-09 | Medium | Call `list_docs` (or inspect the target repo directly) after TS10-07. | The new `specs/product-docs/GUIDE-*.md` file is discoverable alongside `specs/requirements/`/`specs/architecture/` content, not a blind spot in doc listings. | | |
| TS10-10 | Low | Re-run `upsert_user_doc` for the same guide filename with updated content (e.g. ask Dev Team to revise it, or call it directly via the ADK web UI's tool-call interface). | The existing file is updated in place — no second, duplicate `GUIDE-*.md` for the same topic. | | |
